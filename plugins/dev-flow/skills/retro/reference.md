# retro スキル reference——ルールの背景・理由・実測談

`SKILL.md` 本文のルールが「なぜそうなっているか」をここに集約する。ルール自体（何をするか）は本文にあり、このファイルは本文のルールを疑問に思ったとき・改訂するときに読む。

## ルーティング表を使う理由

ふりかえりの価値は、良いアイデアが話しっぱなしで終わると失われる。同じアイデアでも、一度きりか・好みか・厳格なルールかによって定着する仕組みは変わるため、行き先を表で明示的に選び、なぜその行き先が合うのかも述べる。

## すべての観察を仕組みに押し込まない理由

過剰な仕組み化は、将来の自分が読み飛ばすべきノイズを増やす。本当に一度きりのことなら、議論の中で名指しすれば十分。

## 手順1: `/insights` をユーザーに依頼する理由

`/insights` は対話型の組み込みコマンド（REPL専用）で、Claude自身やBashからは実行できない。共有されたハイライト（セッション・ツール・トークンのパターン、時間や許可プロンプトの行き先）があると、「Claude Codeの使い方」の観点を印象論ではなく実数で裏付けられる。

## 手順3: 講義ではなく会話にする理由

ユーザーはClaudeに見えないコンテキスト（チーム事情、過去の経緯、環境の制約）を知っている。一方的な提示では、その情報が改善に反映されない。

## 補足: 「最も軽くて持続する仕組みを選ぶ」の意味

毎回発火するhookは「Claudeが覚えていることを祈る」メモリノートに勝つ。ただし一行の好みにhookは不要。教訓が適用されるべき頻度と厳格さに、仕組みの重さを合わせる。

## 補足: 1成果物につき1関心事にする理由

それぞれ独立に対応（実施・見送り・後回し）できるようにするため——`plan-next` が1項目1issueにするのと同じ理由。
