# リリース後レトロスペクティブ

出荷したばかりのリリースを振り返り、学んだことを「次回をより良くする仕組み」に着地させる。ワークフロー上 `release` スキルの後段に位置する（`plan-next` → `ship`/`batch-ship` → `release` → `retro`）。各ルールの背景・理由は同ディレクトリの [reference.md](reference.md) 参照。

`$ARGUMENTS` はリリースしたばかりのバージョン（`v`無しで例: `0.1.0`）。空の場合は最新タグ（`git for-each-ref --count=1 --sort=-creatordate '--format=%(refname:short)' refs/tags`）から推定し、ユーザーに確認する。タグから推定するときは先頭の `v` を除いたものをバージョンとして扱う（以降、タグ名を指すときは`v`付きで表記する）。`--format` 引数はクォートする——`%(...)` を素のまま渡すと PowerShell が `%` を `ForEach-Object` のエイリアスとして解釈し失敗する。

## 仕組み——改善の行き先

合意した各改善は、**実際に定着する最も軽い仕組み**に着地させる。ルーティングにはこの表を使い、なぜその行き先が合うのかも述べる:

| 教訓が… | 行き先 | 理由・方法 |
| --- | --- | --- |
| 繰り返す複数手順の手作業ワークフロー | **スキル**（`.claude/skills/` 等。新規または既存の編集） | 毎回導出し直す代わりに1つの `/command` になる |
| 「今後Xが起きたら必ずYする」（毎回・決定的） | **hook**（`.claude/settings.json`） | ハーネスが強制する——メモリや好みでは「Claudeが思い出すこと」頼みになり実現できない |
| セッションをまたいで残すべき再利用可能な好み・判断 | **メモリ**（`feedback` / `project` / `reference`） | 永続し自動で想起される。whyも一緒に書く |
| 特定のファイル/パスに固有のガードレール | **path-scoped rule**（`paths` frontmatter付き `.claude/rules/*.md`） | スコープが明確でバージョン管理される——settingsのインラインglobより優先 |
| プロジェクト全体の原則・制約 | **CLAUDE.md** | そのリポジトリでは常にコンテキストに載る |
| 独立して委任できる、繰り返し発生する調査 | **agent**（`.claude/agents/`） | 並列実行・引き渡しができる |
| 先送りする具体的な作業 | **GitHub issue**（`plan-next` の規約に沿ってラベル+マイルストーン） | issue駆動にしておけば何も失われない |

すべての観察を仕組みに押し込まない。本当に一度きりのことなら、議論の中で名指しすれば十分。

## 手順

1. **実際に起きたことを再構成する** — 記憶ではなく証拠に基づく。`node "${CLAUDE_PLUGIN_ROOT}/scripts/release-evidence.js" <バージョン（`v`無し。例: 0.4.0）>` を実行し、CHANGELOGの該当バージョン節・マイルストーンissue一覧（番号・タイトル・ラベル・状態）・前タグから対象タグまでのコミットログ・同期間にマージされたPR一覧・同期間のCI再実行/失敗履歴（`gh run list`ベース）を1回のJSON呼び出しでまとめて取得する。CHANGELOG未採用のリポジトリでは `changelog` が `null` になるだけで他のフィールドは通常通り得られる（リリースノートやマージ済みPR一覧で代替）。`milestoneIssues` から計画されていたもの／途中で追加されたもの／外へ先送りされたものを区別する。`ciHistory` と、greenになるまで複数pushを要したPR・途中でスコープが膨らんだPRから摩擦のシグナルを読み取る。
   - Claude Codeの利用データ: ユーザーに `/insights` の実行と結果の共有を依頼する（`/insights` はREPL専用でClaude自身やBashからは実行できない）。ベストエフォートでよく、ユーザーがスキップしたらそのまま進める。
2. **まず自分の観察を用意する** — ユーザーが求めているのは、単なるファシリテーションではなく*Claudeが*気づいたこと。議論の前に、このリリース固有の論点を用意する（一般的なアドバイスではなく、それぞれ手順1の実イベントに紐付ける）:
   - **Keep**: うまくいったので仕組みに落とす価値があること。
   - **Problem**: 摩擦になったこと。対策案と、その対策がどの仕組みに住むべきかを添える。
   - **Claude Codeの使い方**: `/insights` のハイライトと自分の観察を突き合わせ、パターンを具体的な改善に変える——例: 同じコマンドへの許可プロンプトの繰り返し → settingsの許可リスト（環境にあれば `/fewer-permission-prompts` スキル）、繰り返している複数手順の手作業 → スキルかhook、セッションのたびに説明し直していること → メモリ。提案は必ずデータ上の具体的なパターンに紐付ける。
   - **意外だった点**: 期待と違ったこと（間違っていたワークフローの仮定、メモリに記録する価値のある環境のクセ）。
3. **ユーザーと議論する** — 自分の観察を提示し、ユーザーの観察も引き出す。Keep / Problem（ユーザーの言葉では「うまくいったから仕組みに反映したいこと」「うまくいかなかったから対策を仕組みに反映したいこと」）に、Claude Codeの使い方の提案と意外だった点を加えて構成する。講義ではなく会話にする。候補が多いときは `AskUserQuestion` で「今対応する価値があるもの」に収束させる。
4. **合意した各改善をルーティングする** — ユーザーが対応したい各項目について、表から選んだ行き先の仕組み・行う具体的な変更・*なぜその仕組みか*を述べる。短い計画として提示し、作成前に承認を得る——議論の途中でissueを起票したりファイルを書いたりしない。
5. **承認後に適用する** — 各変更をそれぞれの場所で行う:
   - **メモリ**: Claude Codeの永続メモリ（リポジトリ外・プロジェクトごとのメモリディレクトリ）にメモリファイルを書き、インデックスの `MEMORY.md` に1行のポインタを追加する（リポジトリ外なのでPR不要）。
   - **issue**: `plan-next` の規約に従い、適切な種別+優先度ラベルと（該当すれば）マイルストーンを付けて `gh issue create`。
   - **hook / settings**: 正確な `settings.json` の変更を提案する（hookはハーネスが所有する。設定変更を支援するスキルが環境にあればそれを使う。例: `/update-config`）。
   - **スキル / rule / CLAUDE.md の編集**: 追跡対象ファイルなので、そのリポジトリのGitHub Flowに従う——最新の `origin/main` からブランチを切り、編集し、PRを開き、CIがgreenになったらマージする（`ship` スキルと同じ流れ。関連する仕組みの編集は1つのPRにまとめてよい）。
   - 外向きの作用があるものは実行前に確認する。
6. **報告する** — 各改善とその着地先（issue番号・メモリファイル・PR・hook）を列挙し、意識的に先送りしたものも（失われないようポインタ付きで）述べる。

## 補足

- **`plan-next` ではない。** `plan-next` は*次にどの機能を作るか*を前向きに決める。`retro` は終わったばかりのリリースに基づいて*働き方*を後ろ向きに改善する。retroからissueが生まれることはあるが、それはプロセス/ツーリングの改善であって機能ではない。次バージョンのスコープを決めたくなったら `plan-next` に、新規の機能案の洗い出しは `propose-improvements` に引き継ぐ。
- 1成果物につき1関心事。それぞれ独立に対応できるようにする。
- 最も軽くて持続する仕組みを選び、教訓が適用されるべき頻度と厳格さに仕組みの重さを合わせる。
- retroでこのセッションには大きすぎる作業が浮かんだら、消えてなくならないようissueとして起票する（まだスコープに入れないならマイルストーン無しで）。
