# リリース後レトロスペクティブ

出荷したばかりのリリースを振り返り、そこで学んだことをプロジェクトの働き方への持続的な改善に変換する。目的は不満の発散でも、気持ちのよいまとめを書くことでもない——そのリリースが実際に教えてくれたことに気づき、各教訓を「次回をより良くする仕組み」に着地させることにある。このスキルはワークフロー上 `release` スキルの後段に位置する（`plan-next` → `ship`/`batch-ship` → `release` → `retro`）。

`$ARGUMENTS` はリリースしたばかりのバージョン（例: `0.1.0`）。空の場合は最新タグ（`git tag --sort=-creatordate | head -1`）から推定し、ユーザーに確認する。

## 仕組み——改善の行き先

ふりかえりの価値は、良いアイデアが話しっぱなしで終わると失われる。合意した各改善は、**実際に定着する最も軽い仕組み**に着地させる。ルーティングにはこの表を使い、なぜその行き先が合うのかも述べる——同じアイデアでも、一度きりか・好みか・厳格なルールかによって行き先は変わる:

| 教訓が… | 行き先 | 理由・方法 |
| --- | --- | --- |
| 繰り返す複数手順の手作業ワークフロー | **スキル**（`.claude/skills/` 等。新規または既存の編集） | 毎回導出し直す代わりに1つの `/command` になる |
| 「今後Xが起きたら必ずYする」（毎回・決定的） | **hook**（`.claude/settings.json`） | ハーネスが強制する——メモリや好みでは「Claudeが思い出すこと」頼みになり実現できない |
| セッションをまたいで残すべき再利用可能な好み・判断 | **メモリ**（`feedback` / `project` / `reference`） | 永続し自動で想起される。whyも一緒に書く |
| 特定のファイル/パスに固有のガードレール | **path-scoped rule**（`paths` frontmatter付き `.claude/rules/*.md`） | スコープが明確でバージョン管理される——settingsのインラインglobより優先 |
| プロジェクト全体の原則・制約 | **CLAUDE.md** | そのリポジトリでは常にコンテキストに載る |
| 独立して委任できる、繰り返し発生する調査 | **agent**（`.claude/agents/`） | 並列実行・引き渡しができる |
| 先送りする具体的な作業 | **GitHub issue**（`plan-next` の規約に沿ってラベル+マイルストーン） | issue駆動にしておけば何も失われない |

すべての観察を仕組みに押し込まない。本当に一度きりのことなら、議論の中で名指しすれば十分——過剰な仕組み化は、将来の自分が読み飛ばすべきノイズを増やす。

## 手順

1. **実際に起きたことを再構成する** — 記憶ではなく証拠に基づいてふりかえる。リリースされたバージョンについて以下を集める:
   - CHANGELOGの `x.y.z` セクション（ユーザー視点で何が出たか。CHANGELOG未採用のリポジトリではリリースノートやマージ済みPR一覧で代替する）。
   - マイルストーンのissue: `gh issue list --milestone "vX.Y.Z" --state all --limit 200 --json number,title,labels,state`。計画されていたもの／途中で追加されたもの／外へ先送りされたものを区別する。
   - 前リリースからの変更範囲: 前のタグを見つけ（`git tag --sort=-creatordate` → このバージョンの1つ前）、`git log <prev-tag>..vX.Y.Z --oneline` とマージ済みPR（`gh pr list --state merged --base main --limit 200 --search "merged:>=<前リリース日>"`）を読む。
   - 摩擦のシグナル: それらのPRでのCI再実行・失敗（`gh run list`）、greenになるまで複数pushを要したPR、途中でスコープが膨らんだPR。
   - Claude Codeの利用データ: ユーザーに `/insights` の実行と結果の共有を依頼する。`/insights` は対話型の組み込みコマンド（REPL専用）で、Claude自身やBashからは実行できないため、ユーザーに促し、共有されたハイライト（セッション・ツール・トークンのパターン、時間や許可プロンプトの行き先）を読む。これで下記「Claude Codeの使い方」の観点を印象論ではなく実数で裏付けられる。ベストエフォートでよい: ユーザーがスキップしたらそのまま進める。
2. **まず自分の観察を用意する** — ユーザーが明示的に求めているのは、単なるファシリテーションではなく*Claudeが*気づいたこと。議論の前に、具体的でこのリリース固有の論点を用意する（一般的なアドバイスではなく、それぞれ手順1の実イベントに紐付ける）:
   - **Keep**: うまくいったので仕組みに落とす価値があること。
   - **Problem**: 摩擦になったこと。対策案と、その対策がどの仕組みに住むべきかを添える。
   - **Claude Codeの使い方**: `/insights` のハイライトと自分の観察を突き合わせ、パターンを具体的な改善に変える——例: 同じコマンドへの許可プロンプトの繰り返し → settingsの許可リスト（環境にあれば `/fewer-permission-prompts` スキルがまさにこれをやる）、繰り返している複数手順の手作業 → スキルかhook、セッションのたびに説明し直していること → メモリ。提案は必ずデータ上の具体的なパターンに紐付け、一般的な「もっとうまく使おう」にしない。
   - **意外だった点**: 期待と違ったこと（間違っていたワークフローの仮定、メモリに記録する価値のある環境のクセ）。
3. **ユーザーと議論する** — 自分の観察を提示し、ユーザーの観察も引き出す。Keep / Problem（ユーザーの言葉では「うまくいったから仕組みに反映したいこと」「うまくいかなかったから対策を仕組みに反映したいこと」）に、Claude Codeの使い方の提案と意外だった点を加えて構成する。講義ではなく会話にする——ユーザーはClaudeに見えないコンテキストを知っている。候補が多いときは `AskUserQuestion` で「今対応する価値があるもの」に収束させる。
4. **合意した各改善をルーティングする** — ユーザーが対応したい各項目について、表から選んだ行き先の仕組み・行う具体的な変更・*なぜその仕組みか*を述べる。短い計画として提示し、作成前に承認を得る——議論の途中でissueを起票したりファイルを書いたりしない。
5. **承認後に適用する** — ユーザーの承認が出たら、各変更をそれぞれの場所で行う:
   - **メモリ**: ファイルを書き、`MEMORY.md` に1行のポインタを直接追加する（メモリはリポジトリ外なのでPR不要）。
   - **issue**: `plan-next` の規約に従い、適切な種別+優先度ラベルと（該当すれば）マイルストーンを付けて `gh issue create`。
   - **hook / settings**: 正確な `settings.json` の変更を提案する（hookはハーネスが所有する。設定変更を支援するスキルが環境にあればそれを使う。例: `/update-config`）。
   - **スキル / rule / CLAUDE.md の編集**: これらは追跡対象ファイルなので、そのリポジトリのGitHub Flowに従う——最新の `origin/main` からブランチを切り、編集し、PRを開き、CIがgreenになったらマージする（`ship` スキルと同じ流れ。関連する仕組みの編集は1つのPRにまとめてよい）。
   外向きの作用があるものは実行前に確認する。
6. **報告する** — 各改善とその着地先（issue番号・メモリファイル・PR・hook）を列挙し、意識的に先送りしたものも（失われないようポインタ付きで）述べる。

## 補足

- **`plan-next` ではない。** `plan-next` は*次にどの機能を作るか*を前向きに決める。`retro` は終わったばかりのリリースに基づいて*働き方*を後ろ向きに改善する。retroからissueが生まれることはあるが、それはプロセス/ツーリングの改善であって機能ではない。次バージョンのスコープを決めたくなったら `plan-next` に引き継ぐ。新規の機能案の洗い出しは `propose-improvements` の仕事。
- 1成果物につき1関心事。それぞれ独立に対応できるようにする——`plan-next` が1項目1issueにするのと同じ理由。
- 最も軽くて持続する仕組みを選ぶ。毎回発火するhookは「Claudeが覚えていることを祈る」メモリノートに勝つ。ただし一行の好みにhookは不要。教訓が適用されるべき頻度と厳格さに、仕組みの重さを合わせる。
- retroでこのセッションには大きすぎる作業が浮かんだら、消えてなくならないようissueとして起票する（まだスコープに入れないならマイルストーン無しで）。
