# propose-improvements スキル reference——ルールの背景・理由・実測談

`SKILL.md` 本文のルールが「なぜそうなっているか」をここに集約する。ルール自体（何をするか）は本文にあり、このファイルは本文のルールを疑問に思ったとき・改訂するときに読む。

## 手順1: 重複判定前に `bodyTruncated: true` のissueで全文を取り直す理由

`gh-issue-inventory.js` は本文をデフォルトで最大1000文字に切り詰める。切り詰められたissueは、重複判定の決め手になる詳細が1000文字以降にあるかもしれず、見落とすと同じ提案を重複issueとして起票してしまう。

## 手順4: 提案全体をまとめて聞く理由

`AskUserQuestion` は質問数に上限があるため、項目ごとに1問ずつ聞くと提案数が多いときに収まらない。

## 手順5: 設計の候補案を列挙して1つに決めない理由

設計メモに候補案とトレードオフを列挙し「実装時にどれかを選ぶ（PRで決定を明記）」と書いておくと、実装スキル（`ship`）が質問でブロックされずに自律実装でき、決定がPRに監査可能な形で残る。issueの分析は仮説として扱う——検証するのは実装時のテストファーストのステップ。

## 補足: `gh` 呼び出しの実行確認を求める理由

実行された呼び出しは、ツール結果・「バックグラウンドで実行中」の応答・エラーのいずれかを必ず返す。ターンがそのいずれも無いまま終わり、ユーザーが次に発言した場合、その呼び出しは実行されていない（構文ミス）——「実行されたはず」と仮定すると、issueが実際には作られていない事故になる。
