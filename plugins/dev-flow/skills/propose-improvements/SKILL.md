# 改善点・新機能を提案してissue化する

このリポジトリのソースをレビューし、改善点と新機能案を洗い出して、ユーザーの合意を得たうえでGitHub issueとして起票する。ここではバージョンやマイルストーンは決めない——起票したissueをどの次バージョンに入れるかは `plan-next` スキルの仕事、実装は `ship` スキルの仕事。

`$ARGUMENTS` はレビューの観点や対象領域(例: 「パフォーマンス」「エラーハンドリング」)。省略時はリポジトリ全体を対象にする。

## 手順

1. **現状を把握する** — 主要なソースファイルとテストを読む(エントリポイント、コア処理、設定ファイル)。プロジェクトの目的・設計方針がわかるドキュメント(`README.md`、`CLAUDE.md`、`CONTRIBUTING.md` など)があれば読み、何を目指しているリポジトリかを掴む。`node "${CLAUDE_PLUGIN_ROOT}/scripts/gh-issue-inventory.js"` を実行し、既にオープンなissueと重複する提案をしないようにする(マイルストーン情報は使わないので `--milestones-state` は指定しなくてよい)。
2. **コードをレビューして改善点を洗い出す** — 判断する前に必ず読む。正しさのバグ(特にデフォルトで有効な設定・言語・パスでの)、挙動の欠落、スケーラビリティの懸念を探す。各指摘はソース上の具体的な場所(ファイル・関数など)に紐付ける。本物のバグと、あれば嬉しい程度の改善を区別し、その区別を提示時にも残す。
3. **新機能を提案する** — 手順1で把握したプロジェクトの目的・設計方針に合う機能を提案する。既存のトラッキングissue(大きな機能の親issueなど)の子にあたる提案は、その旨を明示する。
4. **ユーザーに提示して起票するものを決める** — 指摘と機能案を、種別(バグ/新機能)・推奨優先度(high/med/low)・根拠とともに表で提示する。`AskUserQuestion` でどれを起票するか確認する——項目ごとに1問ずつではなく、提案全体をまとめて聞く(`AskUserQuestion` は質問数に上限がある)。ユーザーが選ぶまでissueは起票しない。
5. **選ばれた項目をissueとして起票する** — 各項目について、背景 / 期待する挙動 / 設計メモ / 受け入れ基準 のセクション構成で本文を書き、`gh issue create` で作成する(マイルストーン・ラベルはここでは付けない——`plan-next` が次バージョンのスコープを決める際に判定・付与する)。
   - 設計に複数の妥当なアプローチがあるときは、ここで1つに決めない: 設計メモに候補案を列挙し(例: 案1/案2/案3とトレードオフ、推奨があればその旨)、「実装時にどれかを選ぶ(PRで決定を明記)」と書き添える。こうすると実装スキル(`ship`)が質問でブロックされずに自律実装でき、決定がPRに監査可能な形で残る。issueの分析は仮説として扱う——検証するのは実装時のテストファーストのステップ。
   - 1つの提案が複数の子issueに自然に分割できる場合(大きな機能の親子分割など)は、親issueを先に作ってIDを取得し、子issueの作成後にネイティブのsub-issueリンクを張る: `gh api repos/:owner/:repo/issues/<親番号>/sub_issues -F sub_issue_id=<子のid>`(`<子のid>` は `gh api repos/:owner/:repo/issues/<子番号> --jq .id` で取得する)。あわせて親issueに新しい子issueへのリンクをコメントする。
   - 他の既存issueより先にやっておくべき厳密な前提関係に気づいた場合は、依存する側のissue本文に `前提: #N` の一行を入れる(GitHubが自動リンクする)。
6. **報告する** — 作成したissue番号と種別・優先度の一覧を挙げる。次バージョンにどれを入れるかは `plan-next` スキルで決めること、実装は `ship <issue番号>` で行うことを伝える。

## 補足

- これは提案・起票用のスキル: 成果物はissueであって、コードでもマイルストーンでもない。ここで実装を始めない——それは `ship` の仕事。バージョンのスコープや優先度決定・マイルストーン作成も行わない——それは `plan-next` の仕事。
- 起票するissueは1件1関心事にし、それぞれ独立して出荷できるようにする。
- 各 `gh` 呼び出しが実際に実行されたことを確認する。特に手順5のissue作成。実行された呼び出しは、ツール結果・「バックグラウンドで実行中」の応答・エラーのいずれかを返す。ターンがそのいずれも無いまま終わり、ユーザーが次に発言した場合、その呼び出しは実行されていない(構文ミス)——実行されたと仮定せず、修正して再実行する。
