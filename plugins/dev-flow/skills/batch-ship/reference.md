# batch-ship スキル reference——ルールの背景・理由・実測談

`SKILL.md` 本文のルールが「なぜそうなっているか」をここに集約する。ルール自体（何をするか）は本文にあり、このファイルは本文のルールを疑問に思ったとき・改訂するときに読む。

## 前提となる設計判断（なぜこの形か）

- **親はオーケストレーションに徹する** — 多数のissueを親セッションで直列実装すると、issue本文・コード読解・CI watch出力が積み上がり、コンパクション（文脈の要約・欠落）を踏む。サブエージェントに委譲すれば親には結果サマリだけが返る。コールドスタートで総トークンは増えるが、文脈欠落リスクの回避と引き換えに許容する。
- **並列は3〜4件の波に区切る** — セッション上限はアカウント単位の共有リソースであり、全件一斉起動すると上限到達時に全エージェントが同時に停止し、進行中の作業がまとめて失われる（実測: 8並列で全滅しコミットゼロでやり直しになった事例がある）。波に区切れば全滅しても被害は1波分に限定される。
- **4件以下なら親で直列 `ship`** — 並列worktreeのセットアップとサブエージェントのコールドスタートは小タスクには過剰。

## 手順1: `--state all` と `--limit` を明示する理由

`gh issue list` / `gh pr list` はデフォルトでopenのみ・件数上限で切られるため、明示しないとクローズ済みの検出や全件取得ができず、未完了があるのに完了に見えることがある。

## 手順5: `wave-status.js` が `closedByPullRequestsReferences` を使う理由

issueごとの完了確認は元々 `gh issue list --milestone ... --state all` と `gh pr list --state merged --limit 200` を別々に実行し、両方の生JSONをモデルが突き合わせていた。issue数が多いマイルストーンではこの突き合わせ自体が負荷になる（agent-marketplace#61）。`gh issue view`/`gh issue list` の `closedByPullRequestsReferences` フィールドは issue 単位で「どのPRがこのissueをクローズしたか」を返し、`gh issue list --json closedByPullRequestsReferences` で milestone 一括取得にも使えることを gh 2.86.0 で確認済み（このリポジトリの v0.4.0 波でも実測）。ただしこのフィールドは「リンクされている」ことしか示さず、実際にマージ済みかは別途 `gh pr view <pr> --json state` で確認する必要がある。

## 手順2: 自己変更系issueで先に明示許可を取る理由

エージェント自身の設定・スキルを変更するissueをサブエージェントに委任すると、自動モードの安全分類器に「自己変更」としてブロックされる（「issueをshipして」という一般指示では権限が及ばない）。ブロックされてから都度確認を挟むと手戻りになる。この分類器は正しく安全側に倒れているので、対策は「回避」ではなく「先に確認を取る」こと。

## 手順3: CHANGELOG追記issueを1波あたり最大1件にする理由

CHANGELOGの `[Unreleased]` の同じ見出し（`### Added` 等）に複数エージェントが同時に追記すると高確率で衝突する。内部リファクタ/chore/docs系（CHANGELOG不要）は衝突源が少ない。

## 手順4: 委任プロンプトに並行ship前提の一文を入れる理由

「他のサブエージェントが同時に別issueをshipしている」と知らせておくことで、PRが `mergeable: CONFLICTING` になった際もサブエージェントが自律的にrebase・force-pushで復旧できる（実測済み）。

## 手順4・7: 手動確認の提案をサブエージェントに報告させ、親が一覧にまとめる理由

操作感に影響する変更の手動確認提案（背景は `ship` スキルの reference「手順14」参照）は、diffを実際に読んだサブエージェントにしか書けない——親はコードを読まない分担のため。一方、波ごとにバラバラに提案されるとユーザーは会話ログを遡って拾い集めることになるので、親が最終報告の末尾に一覧として集約する。「基準が欠けていれば補う」のは、試し方だけの提案では何をもってOKと判断するか分からず確認がスキップされがちになるため。

## 手順5・補足: 完了確認をリモートの実状態で行う理由

サブエージェントの最終報告は「マージまで完了した」ように読めても、実際にはCI待ちやマージ前で停止していることがある。
