# 次期リリースを計画する

次バージョンのスコープ決めフェーズを実行する: すでに存在するissueを見て、次に何を出すかを決め、そのためのマイルストーンを準備する。issueが既にトラッカーに存在する状態から始まり、マイルストーンを作成した時点で終わる。新規の改善案・機能案の洗い出しは `propose-improvements` スキルの仕事。各ルールの背景・理由は同ディレクトリの [reference.md](reference.md) 参照。

`$ARGUMENTS` は目標バージョン（`v`無しで例: `0.2.0`）。空の場合は、どのissueを選んだか確定してから（手順4を参照）推定し、ユーザーに確認する。リポジトリがSemVer的なバージョン管理をしていない（`package.json` 等が無い）場合は、手順5・手順1のバージョン取得部分を省略してよい。

## 手順

1. **現状を把握する** — `node "${CLAUDE_PLUGIN_ROOT}/scripts/gh-issue-inventory.js" --milestones-state=all` を実行し、オープンなissue一覧（番号・タイトル・ラベル・マイルストーン・本文）と全マイルストーン（手順6の重複チェックで使う）をまとめて取得する。
   - 標準エラー出力に `::warning::Open issue count reached the --limit` で始まる警告が出た場合、オープンissueが1000件の上限に達しており棚卸しが不完全な可能性があるので、その旨をユーザーに報告する。
   - バージョン管理をしているリポジトリでは現在のバージョン（例 `package.json` の `version`）もあわせて読む。
   - すでにオープンなマイルストーンに入っている（スコープ決定済みの）issueは、ユーザーから指示がない限り対象外とする。
2. **不足しているラベルを補う** — まず `gh label list` で既存のラベル体系を確認する。
   - 種別（`bug` / `enhancement` / `documentation` / `refactor` / `ci` / `chore` など）と優先度（`priority:high` / `priority:med` / `priority:low` など）の2軸（または類似の体系）が既にある → それに従う。
   - 無い → ユーザーに簡単な体系を提案し、合意を得てから使う。このスキルが前提とする2軸の体系を勝手に押し付けない。
   - ラベルは既存のもの以外を無闇に作らず、無いものだけ `gh label create` で作成する。
   - 種別/優先度ラベルが付いていない候補issueは、タイトルと本文を読んで判定し、`gh issue edit <n> --add-label <種別> --add-label <優先度>` で付与する。
3. **候補issue間の前提関係・お得な順序を洗い出す** — `bodyTruncated: true` のissueは `gh issue view <n> --json body` で全文を取り直してから読む。各候補issueの本文にある依存関係のヒント（`関連: #N`、`前提: #N`、タスクリストの参照）と、`gh api repos/:owner/:repo/issues/<n>/sub_issues` 等でネイティブな関係も確認し、「どのissueがどのissueより前に必要か」という**厳密な**依存リストを作る。
   - 前提issueそのものが今回選ばれていない（かつクローズもされていない）issueは今回選定できない——黙って外すのではなく、その矛盾をユーザーに提示する。
   - 厳密な依存ではないが「先にXXをやっておくとYYが安く済む」という**お得な順序**（例: リファクタしてから機能追加すると手戻りが減る）も見つけて記録する。選定可否には影響しないが、手順6の推奨着手順序に反映する。
4. **ユーザーとスコープを決める** — オープンな候補を表で提示する: 番号、タイトル、種別、優先度、前提issue、次バージョンへの採否（推奨）。`AskUserQuestion` で、issueごとに1問ずつではなく、採否案全体（推奨をそのまま承認する／特定の項目を外す／見送り扱いのissueを1つ昇格する、など）として確認する。
5. **バージョンの上げ方を決める**（バージョン管理をしているリポジトリのみ）— 最終的な選定内容に基づく:
   - 破壊的・非互換な変更がある → **メジャー**を上げる。
   - 機能追加（`enhancement`）がある → **マイナー**を上げる。
   - それ以外（バグ修正/ドキュメント/雑務のみ）→ **パッチ**を上げる。
   現在のバージョンから `vX.Y.Z` を計算し、`$ARGUMENTS` が未指定、またはこのルールと食い違う場合はユーザーに確認する。
6. **マイルストーンを作成する** — タイトルは `vX.Y.Z`（バージョン管理をしていないリポジトリでは、日付やコードネームなど適切なタイトルをユーザーに確認する）。全一覧の事前チェックではなく、まず作成を試みて重複エラーで分岐する:
   - `gh api repos/:owner/:repo/milestones -f title="vX.Y.Z" -f state="open" -f description="..."` を実行する。
   - 成功 → それを使う。
   - `422`（同名重複）→ `node "${CLAUDE_PLUGIN_ROOT}/scripts/gh-issue-inventory.js" --milestones-state=all` を再実行し、`milestones` からタイトル `vX.Y.Z` を探す:
     - `state` が `open` → 既存のマイルストーンとしてそのまま使う。
     - `state` が `closed` → そのバージョンは既にリリース済み（または誤ってクローズ済み）の異常な状態。作成・流用せずユーザーへ報告する。
   - `description` は、他のセッションやスキルがユーザーに聞き直さずに計画を引き継げるリリースの共有ブリーフとして書く:
     - リリースのテーマ・目的を一行で。
     - 選定したissueの**推奨着手順序**（厳密な依存関係を最優先、次にお得な順序、その次に優先度）。例: `1. #12 → 2. #9(#12に依存) → 3. #7(#15より先にやると安上がり) → 4. #15`
     - 見送った項目とその理由（前提未達、次バージョン以降に持ち越し、など）。
   - 複数行のテキストは一時ファイルに書き、`gh api --method PATCH repos/:owner/:repo/milestones/<番号> -F description=@<ファイル>` で渡す（`--method PATCH` は必須）。
7. **文章だけでなく、issue単位の関係も設定する** — マイルストーンの説明文だけに順序情報を頼らない:
   - 選定した全issueをマイルストーンに割り当てる: `gh issue edit <n> --milestone "vX.Y.Z"`。
   - 親issueをサブタスクに分割したような関係には、GitHubネイティブのsub-issues機能を使う: `gh issue edit <親> --add-sub-issue <子>`（または `gh issue edit <子> --parent <親>`。使えない場合は `gh api repos/:owner/:repo/issues/<親>/sub_issues -F sub_issue_id=<子のid>`）。
   - 親子関係ではない「先にこれが必要」という順序依存には、依存する側のissue本文に `前提: #N` の一行を（まだ無ければ）追記する（GitHubが自動リンクする）。
8. **報告する** — マイルストーンのURL/番号、選定したissue一覧（最終的なラベルと推奨順序付き）、スコープ外にしたissueとその理由を挙げる。各issueは `ship <n>` で実装すること、全issueがクローズしたらマイルストーン完了で `release` に引き継ぐことも伝える。

## 補足

- これはスコープ決定用のスキルであり、成果物はマイルストーン・ラベル・関係性であって、コードでも新規issueでもない。棚卸し中に本当に足りていない改善点・新機能案に気づいた場合は、その場で起票せず `propose-improvements` スキルに譲る。
- ラベルの2軸（種別・優先度）は独立に保つ。検討対象になったissueは、それぞれ1つずつ必ず持つようにする。
- 引き継ぎには独自フォーマットを発明せず、GitHub自体の仕組みを優先する: 物語・順序はマイルストーンの `description`、親子関係はネイティブのsub-issues、単純な順序依存は `前提: #N` のテキスト参照。
- 手順2・6・7でのラベル/マイルストーン作成やissue編集の `gh` 呼び出しが、実際に実行されたことを都度確認する。ターンがツール結果もエラーも無いまま終わっていた場合、その呼び出しは実行されていない——実行されたと仮定せず、修正して再実行する。
